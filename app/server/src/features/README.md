# features

Backend feature modules, mirroring the frontend's feature folders.

- `authors/` — full CRUD for author profiles and their writing samples (Milestone 3).
- `products/` — full CRUD for products, including local image uploads (Milestone 4).
- `article-types/` — read-only listing of the seeded article types (Milestone 5A). No create/edit/delete — that data is seeded reference data, not user-editable here.
- `dashboard/` — read-only aggregate counts (authors, products, articles) for the Dashboard (Milestone 5A).
- `articles/` — draft persistence for the full Content Brief workflow: article type, author, product, topic, working title, keywords, and content brief fields (Milestone 6, extending the minimal version from 5B). Create, update (full-replace), fetch a draft by id, and (Milestone 7) `GET /:id/prompt` to retrieve its assembled prompt. Still no article content/body editing, no list/delete endpoints, no AI, no publishing.
- `prompt-builder/` — assembles the complete prompt text (article + author + optional product + content brief + instructions) from a draft already in the database, with the required-field validation described in Milestone 7. Pure text assembly — calls no AI model, sends nothing externally.
- `ai-providers/` — AI provider configuration, the model registry, model capabilities and model validation. API keys are never stored in SQLite or returned by the API — see `shared/secrets/providerSecrets.ts`. Only one default provider system-wide. `modelCapabilities.repository.ts` (Milestone 15) holds the SET of jobs a model may do, one default per capability rather than one per model, so a model can be the default article writer *and* the default SEO reviewer. `modelValidation.service.ts` (Milestone 15) validates a model before it is saved — `configuration → endpoint → credential → catalogue → live probe → normalisation` — and the ordering is the diagnosis: whichever stage fails names the real problem rather than the symptom. A free model is probed live; a paid one is never contacted without explicit permission.
- `model-router/` — given a task type, returns which provider/model is configured to handle it. Pure lookup — never contacts a provider, never returns an API key value. Since Milestone 15 it reads the default from `ai_model_capabilities` and **refuses a model not registered for the requested task**, so purpose separation is enforced by the router rather than only by the picker.
- `generation/` — the AI generation engine (Milestone 9): draft → Prompt Builder → Model Router → provider adapter → configured model → normalized response → saved back to the draft, with one `generation_history` row per attempt. `providers/` holds one adapter per provider type (OpenRouter, Anthropic, OpenAI), all behind the single `ProviderAdapter` interface in `generation.types.ts`, so adding a provider means adding one file and one registry entry. Adapters are the only code that knows a vendor's API shape, and the only code that ever sees a key. The task type is a parameter throughout, so future tasks (title generation, SEO review, quality review) route through the same path. Generation never changes an article's status — drafts stay unpublished until a human approves them. Endpoints live on `articles/` (`GET /:id/generation`, `POST /:id/generate`, `GET /:id/generation-history`), mirroring how Milestone 7 put `GET /:id/prompt` there.

- `cms/` — the CMS connector layer (Milestone 13): `CYNTH → CMS Connector → WordPress`. The connector contract has no publish operation at all, so draft-only is structural rather than procedural. `seoAdapter.ts` (Milestone 14) maps Cynth's SEO metadata onto the CMS-independent `CmsSeoMetadata`; its `SeoFieldMapping` registry is deliberately empty, so no SEO plugin is named anywhere.
- `seo/` — the SEO Engine (Milestone 14). `seoDocument.ts` parses the article body into an addressable structure so findings can point at a passage; `seoDeterministic.service.ts` runs the free, code-decided checks; `seoAi.service.ts` + `seoPrompt.service.ts` + `seoAi.parse.ts` run the AI-assisted pass through the existing Model Router (`seo_review` purpose) and treat the model's output as untrusted; `seoScore.service.ts` produces a score that excludes what it did not examine; `seoGate.service.ts` decides SEO readiness; `seoAnalysis.service.ts` orchestrates all of it. **Nothing in this feature writes to the `articles` table** — SEO lives in its own tables beside the article, so an analysis can be run, discarded and re-run without the article changing.
- `web-intelligence/` — the web intelligence and backlink foundation (Milestone 14), **deferred to Phase 2 (Milestone 15)**. Architecture only: `retrievers/index.ts` is an **empty registry**, so Cynth has no code path that can fetch a web page — verified rather than assumed, and the UI now says so. The data model enforces provenance — a finding requires a retrieval, a retrieval requires a user-created web source, and both source permissions default to off.
- `quality-gate/` — the Quality Gate (Milestone 15). Fifteen deterministic checks in three groups, each reporting its own verdict and its own sentence explaining it; blocking failures decide Failed, warnings never do, advisories are reported and never counted. `qualityGate.service.ts` is pure and stores nothing, so previewing an article's readiness never mutates it; `qualityGate.repository.ts` persists the latest evaluation and reports a stale one as stale. Deliberately **not** the SEO gate: quality asks whether this is a finished article, SEO asks whether it will perform in search, and an article can pass one while failing the other. Nothing here calls a model or writes to the `articles` table.

`seo/seoStatus.service.ts` (Milestone 15) derives the five-state SEO status from what the SEO engine already stored — it runs no analysis and adds no second SEO system. The client's `seo-review/` page is the cross-article SEO view and `quality-gate/` is the cross-article readiness view; the per-article work happens on the Article, where both statuses are shown as a pair.
